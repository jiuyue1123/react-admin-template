# 教训沉淀 LESSONS

> CLAUDE.md 规则 2：**项目会话开始时回顾本文件**；用户每次纠正后，将可复现的模式追加到此处（Why / How to apply），持续迭代直到错误率下降。

## 1. 「构建成功」不等于「运行正确」——必须跑到真实运行时

**现象**：访客端 `next build` 全绿，但 `pnpm start` 直接报
`"next start" does not work with "output: standalone"`；手工复制静态资源后启动，
CSS 又 404。若不实际启动，会带着一个跑不起来的部署产物交付。

**Why**：构建只验证编译与打包；运行时装配（standalone 产物结构、静态资源位置、
环境变量）不在构建的检查范围内。

**How to apply**：涉及部署形态的改动，必须完成「构建 → **启动** → curl 关键路径」
三步。本次即由这一步发现了 standalone 的产物路径是
`.next/standalone/apps/site/`（monorepo 下多一层）以及静态资源需手动拷贝。

## 2. 验证要看「状态码 / 协议层」，不能只看页面内容渲染对了

**现象**：`/not-exist` 页面正确地渲染出了「页面不存在」，肉眼完全正常，但 HTTP
状态码是 **200**（软 404）。搜索引擎会把这类响应当作正常页面收录。

**Why**：`src/app/loading.tsx` 会建立 Suspense 边界，响应先以 200 开始流式输出；
此后无论从 page、同段 layout 还是 `generateMetadata` 抛 `notFound()`，都改不了已发出
的状态码。我试了三种位置都无效，最终只能移除 `loading.tsx`。

**How to apply**：凡改动涉及重定向、404、缓存头、SEO 语义，验证时必须显式检查
**状态码与响应头**，而不是只看页面渲染结果。`curl -o /dev/null -w '%{http_code}'`。

## 3. 不要凭「依赖里没有 `"use client"`」就断定它 RSC 安全

**现象**：`@ant-design/icons/es/index.js` 没有 `"use client"`，据此判断它可在服务端
渲染。实际构建时报 `createContext is not a function`——图标组件依赖的
`AntdIconLight` 才带 `"use client"`，且模块作用域调用了 `createContext`。

**Why**：RSC 安全性取决于**实际渲染路径上的每一个模块**，而不是入口文件的表面特征。

**How to apply**：判断某个依赖能否在 RSC 中使用，要跟到它最终渲染用到的那个模块，
并看它是否调用 `createContext` / `useState` 等客户端专有 API。最可靠的验证是
**构建一次**，而不是读代码推断。

## 4. 打包器的代码隔离要验证产物，不能假设配置生效

**现象**：为让访客端只拿到「渲染用」的区块，我给 `builder-blocks` 配了
`index` / `render` 两个 lib 入口。结果 rollup 把共用模块抽成了一个共享 chunk，
编辑器专用的 `media-field`（含 `createContext`）被并入其中，渲染入口**依然**能触达它。

**Why**：多入口时打包器按「模块被哪些入口共用」重新分块，源码层面的入口划分不等于
产物层面的隔离。

**How to apply**：任何「隔离依赖/减小包体」的构建改动，都要对**产物**做断言
（本次做法：`scripts/check-rsc-safety.mjs`，检查 dist 里是否出现禁用 API，挂在 build 上）。
最终解法是去掉构建层的复杂度，改为在源码层消除依赖（`createContext` → 模块级注册）。

## 5. 空值兜底不能返回「看起来像空对象」的值

**现象**：`parseContent` 解析失败返回 `{}`。Puck 的服务端渲染实现是
`"props" in data.root ? ...`，`data.root` 为 `undefined` 时直接抛
`TypeError: Cannot use 'in' operator`。

**Why**：`{}` 对调用方是 truthy，绕过了 `if (!data)` 这类判空；而下游按结构访问字段时
才炸。

**How to apply**：容错解析一律返回**结构完整的空文档**（这里是
`{ root: { props: {} }, content: [] }`），而不是 `{}`。admin 的 `utils/sitePage.ts`
与访客端的 `lib/puck.ts` 已统一。

## 6. 本地工具链的路径/编码坑（Windows + Git Bash）

**现象**：同一个 `/tmp/x.json`，bash 能读写，Windows Python 却报 FileNotFound——
Git Bash 的 `/tmp` 是 `C:/Users/<user>/AppData/Local/Temp`，而 Windows Python 把
`/tmp` 解析成当前盘符根目录的 `C:\tmp`。

**现象 2**：用 `curl -d '{"tenantName":"星辰汽修"}'` 传中文，后端返回
`10003 请求体无效`；同样的数据写成 UTF-8 文件后用 `--data-binary @file` 就正常。

**How to apply**：本地脚本传中文载荷一律**写文件再 `--data-binary @file`**，不要走
命令行或管道；跨 bash/Python 共享临时文件时用 Windows 绝对路径。

## 7. 文件扩展名必须与内容匹配（`.ts` 不能写 JSX）

**现象**：新建 `src/hooks/useQuotaGate.ts`，里面为 `modal.info` 的 content 写了 JSX，
dev server 直接报 `Unexpected token, expected ","`，指向 `<div` 那一行。

**Why**：Vite/Babel 按扩展名决定是否启用 JSX 解析，与文件里有没有 React import 无关。
项目里 `.ts` = 纯逻辑（`utils/*.ts`、`store/*.ts`），`.tsx` = 含 JSX
（`components/*.tsx`、`pages/**/index.tsx`），这个划分是硬的。

**How to apply**：写文件前先问一句「这里面有 JSX 吗」。有就是 `.tsx`——
**hook 里渲染弹窗内容同样算**（`hooks/useQuotaGate.tsx`）。
重命名不需要改引用：项目内 import 都是 extensionless 的。

## 8. 不要把「照同类东西类推」的结果当成事实说出口

**现象**（2026-09-26，与后端 agent 对齐表单需求时连犯两次）：

1. **枚举取值域**：我把表单状态写成 `0草稿/1启用/2停用`，并当成「原始约定」。实际是 `0停用/1启用`（没有 2）。
   **根因**：`Api.SitePage.PageState`（页面状态）恰好是 `0草稿/1已发布/2已下线` —— 我照它类推，把「页面」的语义搬到了「表单」上。
2. **字段位置**：我说「后端早先提过 `guestId` 复用 `X-Guest-Id` 请求头」。后端从未这样约定，实现是 **body 字段**。
   **根因**：`jff-support` 的 `VisitorSupportController` 真的用 `@RequestHeader("X-Guest-Id")` —— 我读了真代码，但那是**客服会话的身份键**（检索/发消息都靠它），表单的 `guestId` 是纯信息性字段，语义不同。

**Why**：两处都不是凭空编的，恰恰相反——都是**读到了真实存在的东西，然后把它类推到了不适用之处**。这种错误比纯粹的幻觉更危险：它有「依据」，所以自己不会怀疑；而 TypeScript 也拦不住（`0|1|2` 都能通过，只是判断会错一半）。

**How to apply**：
- 涉及**枚举取值域、字段名、字段位置**这类契约事实时，**只认对方给的闭集**，不要从「同类东西」推。没给闭集就**去问**，别猜。
- 定义类型时，**给同形但语义不同的枚举写醒目注释**（见 `typings/api/siteForm.d.ts` 的 `FormState`，把 `PageState` / `LeadState` 的差异并列写出），让别人（和以后的自己）不会套错。
- 引用别人的约定时，**区分「我读代码推出来的」和「对方明确说的」**。前者要标注为推断并去求证，不能陈述为事实。

## 9. 逐字符规范化时，不要做「终结性处理」——用户会输不进合法值

**现象**（2026-09-26，用户实测发现）：表单标识输入框要填 `contact-us`，打到 `contact-` 时
**连字符当场消失**，接着敲 `u` 得到的是 `contactu` —— 这个值**根本打不出来**。

**根因**：我在 `onChange` 里做规范化时顺手裁了首尾连字符
（`.replace(/^-+|-+$/g, '')`）。每次按键都执行一遍，于是 `contact-` 的结尾 `-` 被当成
「首尾多余字符」立即裁掉。**终结形态的规则被套在了中间态上。**

同一处还有第二个毛病：`pattern` 校验按默认的 `onChange` 触发，打到 `contact-`
就中途报错——**同样是因为拿最终形态去校验中间态**。

**Why**：输入框里的值是**逐步演化**的，中间态天然不满足最终形态的约束。把
「trim / 补全 / 格式校验」这类终结性处理放进逐字符路径，用户就永远走不到终点。

**How to apply**：
- `onChange` 只做**单调、不丢信息**的规范化：转小写、非法字符替换、限长。
  **不要 trim 边界、不要补全、不要做格式校验。**
- 终结性处理放到 **`onBlur`**（裁首尾、补默认值）与 **提交时**（完整校验）。
- 带模式的字段用 `validateTrigger="onBlur"`，别让用户在输到一半时看到红字。
- 自查问法：**「用户要输入的值，能不能一个字一个字地敲出来？」** 中间态会被规范化
  抹掉的话，就是这个问题。

## 10. 比较两个值之前，先确认它们**同口径**

**现象**（2026-09-26，用户实测撞到）：表单提交的跨站校验返回 `10003 请求来源不合法`，
**同源提交也被拦**。

```ts
const originHost = new URL(origin).host   // 'localhost:3001'  —— 带端口
const host = await getRequestHost()       // 'zzformtest.jianfanfang.com' —— 不带端口，且被 DEV_SITE_HOST 替换过
originHost !== host                       // 必然不等
```

**两处错误叠在一起**：
1. **规范化口径不同**：`URL.host` 带端口，`getRequestHost()` 内部的 `normalizeHost` 会**去掉端口**。
   即使没有 DEV_SITE_HOST，`localhost:3001` ≠ `localhost`，照样拦。
2. **语义口径不同**：跨站校验要比的是「**浏览器实际请求的 Host**」，我却拿了
   「**解析出来的租户 Host**」。这两个在开发环境里**故意不同**（DEV_SITE_HOST 就是干这个的），
   所以这个校验在本地**永远不可能通过**。

**Why**：两个变量名字都叫 host、都是字符串，看起来可以直接比。但它们经过了不同的处理管道、
承载着不同的概念。这种 bug 在单测里也很难发现——因为**只有真实环境才会让两者不同**。

**How to apply**：
- 写比较前问三句：**两边是否经过同一套规范化？（端口、大小写、尾斜杠）**、
  **两边代表的是同一个概念吗？（请求地址 vs 业务身份）**、**在开发/生产两种环境下还成立吗？**
- 尤其是「安全校验」这类**不通过就拦截**的逻辑：它的失效方向是**把正常用户挡在外面**，
  比漏放更伤。写完必须**在真实环境里跑一遍正例**，不能只推理。
- 用「源头的原值」比「源头的原值」（都取 header），别拿一个原值比一个加工过的值。

## 11. 分批作业时，「改了」不等于「提交了 + 验证了」——不要把三者混成一句话说

**现象**（2026-09-26，一次 7 批的文案优化）：批 3b 我改完 4 个文件后直接进入下一批，
**既没提交、也没跑该批的「旧串归零」检查**。随后在交付报告里写了「旧串 grep 全部归零」——
**那句话对批 3b 是没跑过的**。是用户一句「全部 commit」把这段游离的改动翻了出来。

后果实打实：`自定义URL` 有**两处副本**，我只改了列表里的 Tag，漏了新建/编辑表单里的单选选项
（`src/pages/content/menu/index.tsx`）——于是列表显示「自定义链接」、表单还显示「自定义URL」。

**Why**：分批的价值在于「每批独立可验证、可回滚」。某批一旦没有收尾，它就退化成一段游离在
工作区的改动 —— 既不在这批的验证范围内，也会被后续批次的检查自然漏掉。更危险的是：
**「我改过了」的体感会让我以为「我验证过了」**，于是报告里出现根本没跑过的断言。
漏改本身能靠 grep 发现，而**虚假的验证结论会让人停止检查**，这比漏改严重。

**How to apply**：
- 每批的收尾是**一个不可拆的三元组：改 → 跑该批检查 → 提交**。缺一，这批就还没结束。
  **不要**先把几批都改完再统一提交。
- 收尾时显式看一眼 `git status`：**本批的改动必须都已消失**（已提交）。
- 报告里凡出现「全部 / 已归零 / 已通过」，**先问自己：这句检查我真的跑过吗？跑的是哪个范围？**
  没跑过就老老实实写「未验证」。**宁可报告得难看，也不要报告得不实。**
- 可复用的兜底手法（本轮后半段补做，值得常态化）：把 diff 里**被删掉的**每一段中文抽出来
  逐段回查是否还有残留，能机械地发现「同一句话的副本漏改」，比逐条回忆可靠：

  ```bash
  git diff master -U0 | rg -N '^-[^-]' | rg -o '\p{Han}{6,}' | sort -u | while read -r f; do
    for file in $(rg -l -- "$f" src apps | tr '\\' '/'); do
      grep -qxF "$file" <(git diff --name-only master | tr '\\' '/') || echo "漏网副本: $f → $file"
    done
  done
  ```

## 12. 内联 `style` 支配一切 —— 包括自定义属性，也包括媒体查询

**现象**（2026-09-28，区块响应式改造）：区块库 14 个区块全是内联样式，全包没有一处
`@media`。要给它们加响应式，第一反应是「在样式表里写个断点覆盖就行了」——**不行**。
内联 `style` 的优先级高于任何选择器（除非 `!important`），写在 `inline` 里的属性
媒体查询永远覆盖不了。

更反直觉的是第二条：**这条规则对自定义属性同样成立**。
`style={{'--jff-grid-min': '260px'}}` 之后再在 `@media` 里写
`.jff-grid { --jff-grid-min: 160px }` 是**无效的** —— 变量本身也被内联钉死了。
想降级只能让 class 用 `min()` / `clamp()` 把变量**包住**，而不是改写它。

**Why**：这不是「写法偏好」，而是决定了**架构**：一个属性一旦出现在 inline 里，
就永久放弃了响应式能力。所以「哪些属性进 inline」必须在动手前定死，事后补断点
等于返工重写。

**How to apply**：
- 动手前先给属性分类：**需要随断点变化的**（padding / fontSize / maxWidth / gap /
  栅格列）→ 只进样式表，由 class 命中；**每实例不同的**（租户选的色值）→ 进实例
  变量；**绝对色与交互填充** → 可以留在 inline。
- 还有一条与它配套的坑：**Puck 会把 `defaultProps` 写进已保存的节点**，所以
  「字段为空就不输出 inline」这个约定**对存量数据不成立**（老节点里字段是有值的）。
  能覆盖全部存量页面的只有一条路：**把「非字段的写死默认值」搬进 class**。
- 自查问法：**「这条属性以后要随屏幕变吗？」** 要，就别写进 inline。

## 13. 验证脚本会给你假结果 —— 断言前先确认匹配到的是标记，不是同页的样式表文本

**现象**（2026-09-28，同一次改造）：为了验证「Cta 深色底判定没被颜色解析破坏」，
我写了个脚本渲染区块、然后对整段 HTML 做 `html.includes('jff-title--inverse')`
与 `color:` 正则。结果报出「浅灰底也走了 inverse 分支」——看着像个严重 bug。

**根因**：区块自己会渲染 `<style href="jff-builder-blocks">`，**整张样式表就内联在
同一棵树里**。`jff-title--inverse` 和第一个 `color:` 都出现在 CSS 文本中，
所以正则命中的是样式表而不是元素。剥掉 `<style>…</style>` 之后重跑，四项判定
全部正确。

**Why**：这类假结果**方向是随机的** —— 它既可能报出不存在的问题（这次），也可能
在别的形态下**掩盖真问题**（断言「没有 X」时命中 CSS 文本里的 X 就永远为真）。
比没有验证更糟：它给我一个「我验证过了」的错觉。

**How to apply**：
- 断言 DOM 时**先剥掉 `<style>` / `<script>`**，再匹配。或者更稳：匹配
  `class="…"` / `style="…"` 这类**属性**，而不是裸字符串。
- 拿到「异常」结论时，先怀疑**判据**，再怀疑被测对象：把命中的位置打出来看一眼
  （这次只要看一眼上下文就知道是 CSS）。
- 小工具本身也会骗人：`grep -c` 命中 0 时**退出码是 1**，夹在 `&&` 链里会**静默
  截断后续命令**，让人以为后面的检查也跑了。批量检查用 `;` 分隔，别用 `&&`。

## 14. 立论要用**自己职责范围内**的依据 —— 别人的产出是「样例」，不是「标准」

**现象**（2026-09-29，做「可视化编辑器还缺什么组件」的差距分析）：我把简帆坊**官网**
（同工作区的 `marketing` 仓库）当成了「精美网页」的**基准**来立论 —— 说「客户评价这个
版式官网自己都有」「而 `marketing-bak` 里的版本带姓名+职务，改版时反而被砍了」，
还从「官网全站没有一张照片」推出了对租户站点的建议。用户纠正：**官网不是我负责的。**

**Why**：两个问题叠在一起。
1. **依据的权威性不成立**：那个仓库的设计取舍是**另一个团队**做的决定，不是我要满足的
   规格。把别人的产出当作「应该照做的东西」，等于凭空给自己（和用户）立了一个不受认可的
   标准。用户否掉它之后，我的结论虽然还站得住，但论据塌了一半。
2. **越界感**：读别人的代码做参考、和「拿别人的代码当作自己方案的依据」是两件事。
   后者隐含着「他们那里是这样的，所以这里也应该这样」，而我没有资格做这个判断。

**How to apply**：
- 立论前先问：**这条依据在我职责范围内吗？** 不在范围内的事实（别人的仓库、别人的设计、
  别的团队的取舍）只能作为**参考样例**引用，且要**显式标注为样例**；不能作为「应该如此」
  的依据。
- **优先找项目内的、且描述「需求本身」的依据**。这次其实有一条更硬的、我之前没用上的：
  租户在定制首页需求表单里自己填的就是「**含产品、案例、关于三屏**」
  （`src/pages/customization/index.tsx:360` 我们自己写的 placeholder 示例）——
  这比官网的版式更能说明客户要什么。
- 参照系的可信度排序：**用户明确说的 > 需求/契约文档 > 我们自己代码里的既有事实 >
  别人的实现（仅作样例）**。

## 15. 「同一份代码，两个宿主的默认值不一样」—— 别假设默认值一定存在

**现象**（2026-09-29，区块库加富文本字段）：`TextBlock` 新增 `content` 字段，我在
`defaultProps` 里放了样例文案，心想「反正默认值是空的，存量数据不受影响」——
**错了**。Puck 的两条渲染路径对 `defaultProps` 的处理**不一样**：

- 编辑器：`{ ...componentConfig.defaultProps, ...item.props }` —— **合并**
- 访客端 RSC：`{ ...item.props }` —— **不合并**

后果有两层，都很痛：
1. **编辑器侧**：合并意味着 `defaultProps` 里的**非空值会被写进每一个存量节点**
   （不只新节点）。放样例文案 = 所有老正文节点一次性改走富文本分支，租户写的内容
   **一个字都不显示**。这是「一次搞坏所有页面」级的。
2. **RSC 侧**：不合并意味着 `render` 里拿到的字段**可能是 `undefined`**。本次实测：
   手工造一个缺 `items` 的节点，服务端直接抛 `Cannot read properties of undefined`。

**Why**：我把它当成「默认值就是个兜底」——这是单宿主的直觉。**同一个组件被两个
渲染器消费时，默认值的语义可能完全不同**：一边是「新实例的初值」，另一边根本没有。

**How to apply**：
- 组件被两个渲染器消费（编辑器 + SSR/RSC、web + native、dev + prod）时，
  **去读两边的源码确认默认值怎么用**，别按一边的直觉写。
- 默认值取**中性的空值**（空串、空数组）而不是「看起来更友好」的样例值 ——
  样例值会被当数据写进去。
- `render` 里对所有字段都假设可能是 `undefined`；这条和「默认值会被落盘」并不矛盾，
  是同一个机制的两面。
- 自查问法：**「这个默认值会被写进已保存的数据吗？在另一条渲染路径上它存在吗？」**

## 16. 在 CSS 模板字符串里写注释，别用反引号

**现象**（2026-09-29，同一次改造，**连撞三次**）：区块库的样式表是一整段
`` const CSS = `…` `` 模板字符串。我在注释里写「空槽输出 `<div class="jff-col">`」
解释行为 —— 那对反引号**提前终止了字面量**，后面整段 CSS 变成非法 JS。
三次都是同一类：注释里引用 HTML 片段或 Tailwind 类名。

**Why**：这是「在字符串里写字符串」的经典问题，但在**长模板字符串的注释**里特别
隐蔽 —— 写注释时心理上处于「这是文本，随便写」的状态，忘了外层就是字符串。

**How to apply**：
- 模板字符串内的注释里，**引用代码片段一律用引号或「」**，不用反引号。
- 好在 `tsc` 会立刻报 `TS1005`，不会静默出错 —— 但也别指望它，报错行号指向的是
  字面量**之后**的位置，容易先怀疑别处。
- 更彻底的做法是把 CSS 抽到 `.css` 文件；本包因「不能有 CSS 文件」的构建约束
  做不到，所以在**模板字符串顶部写一行提醒**最省事。

## 17. 提「封顶 / 上限」类方案前，先算一遍当前值落在哪 —— 否则它等于没写

**现象**（2026-09-29，编辑器画布宽度）：用户要「画布默认按桌面宽度」。我给了两个选项，
推荐了「**封顶** 1280px（有空间时是 1280，窄了跟着变窄，不出现横向滚动）」，
理由是「改动最小、风险最低」。用户选了它。改完 —— **「没反应呀」**。

查下来原因很简单：Puck 0.23 的界面是「68px 插件条 + 186px 侧栏」，所以编辑器可用区
= 浏览器宽度 − 约 250px。**在 1440/1536 的窗口上可用区本来就只有 1200 左右，
已经小于 1280 —— `max-width: 1280px` 一点作用都没有。**

**Why**：`max-width` 只在「当前值可能超过上限」时才有意义。我推荐时只想了
「有空间时是 1280」，没算「用户的实际空间是多少」。**一个 30 秒的估算就能避免
一次白做的改动 + 一轮来回。**

而且我当时还把它包装成了「推荐」——**推荐意味着我算过**。这个包装让用户放弃了自己
判断，所以责任在我，不在「用户选错了」。

**How to apply**：
- 提任何**阈值类**方案（封顶、限制、下限、超时、缓存条数）之前，先估一遍
  **当前实际值 / 典型实际值**落在阈值的哪一侧。落不到阈值那一侧，这个方案就是
  无效方案，不要提，更不要标「推荐」。
- 估算不出来就说「我需要先量一下」——**别用「改动最小」替代「确实有效」**。
- 自查问法：**「这个上限在什么情况下会被触发？那种情况常见吗？」**
- 同类：给「优化」建议前先确认瓶颈真的在那里；给「兜底」前先确认那条路径真会走到。
